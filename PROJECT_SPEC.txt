SECTION 0 — EXECUTIVE SUMMARY (for the Manager hat)
================================================================================
We are rebuilding an existing OpenCart-based fireworks catalog/enquiry site
(sivakasirobofireworks.in, brand "Robo Crackers", operating since 1985 under
"ROBO Agencies") as a modern, fast, mobile-app-like web application.

Business constraints that shape the whole architecture:
 - Per a 2018 Supreme Court of India order, fireworks CANNOT be sold online.
   The site must remain an ENQUIRY / QUOTE CART model, not a real checkout.
   Customers add items to a cart, submit an enquiry, and the business follows
   up via WhatsApp/phone call to confirm and close the sale offline.
 - Therefore: no payment gateway, no card storage, no online transaction
   processing. This drastically simplifies compliance and security scope.
 - Traffic is highly seasonal (Diwali/Deepavali peak, near-zero the rest of
   the year) — architecture must scale to near-zero cost off-season and
   handle a short, sharp spike in October/November.
 - Many customers are on low-end Android phones with patchy rural/small-town
   internet (Tamil Nadu) — performance on slow 3G/4G is a hard requirement,
   not a nice-to-have.
 - Owner wants an admin panel to manage products, categories, discounts,
   enquiries/orders, and export customer lists to Excel.

Two audiences, two experiences, one codebase:
 1. Public storefront — looks and feels like a native mobile app in the
    browser (app-style top bar, bottom navigation, smooth transitions),
    installable as a PWA, fast on slow networks, and SEO-indexable.
 2. Admin dashboard — a separate, authenticated area for staff to manage
    catalog, enquiries, and customers, and export data to Excel.

SECTION 1 — TECH STACK (Architect hat) — WHY EACH CHOICE
================================================================================
Chosen because the developer is solo, already comfortable with a strongly
typed language (Dart/Flutter professionally), and needs one language across
the whole stack to move fast without context-switching.

FRONTEND
 - Next.js 15 (App Router) + React 19 + TypeScript
     Reasoning: server-side rendering + static generation = best SEO;
     one framework does both frontend pages AND backend API routes.
 - Tailwind CSS v4
     Reasoning: fastest way for a solo dev to build a consistent, responsive,
     "app-like" design system without hand-writing CSS files per component.
 - Framer Motion
     Reasoning: production-grade animation library, small footprint,
     works great for page transitions, add-to-cart micro-animations,
     skeleton-to-content fades — all without hurting load time if used
     selectively (see Section 6, Performance Budget).
 - next-pwa (or Serwist, its maintained successor)
     Reasoning: turns the site into an installable Progressive Web App with
     a service worker, so return visitors get app-icon-on-homescreen,
     offline shell, and instant repeat loads — this is what makes a browser
     site "feel like a mobile app."

BACKEND
 - Next.js Route Handlers (app/api/*) written in TypeScript, running on
   Node.js 20 LTS.
     Reasoning: no second backend project/repo to maintain solo; same
     language and types shared between frontend and backend (see Section 4,
     shared types).
 - Prisma ORM
     Reasoning: type-safe database access, auto-generated types, easy
     migrations — ideal for a solo dev who wants speed with safety.

DATABASE
 - PostgreSQL 16 (hosted: Neon or Supabase — both have serverless/autoscale
   free tiers that fit the "near-zero off-season, spike at Diwali" traffic
   pattern; both support branching for safe testing of schema changes).
     Reasoning: relational integrity for Orders/Customers/Products, strong
     JSON support for flexible product attributes (variations), mature
     tooling.

CACHING LAYER
 - Next.js built-in Data Cache + Full Route Cache (ISR — Incremental Static
   Regeneration) for product/category pages.
 - Upstash Redis (serverless, pay-per-request, fits the seasonal-traffic
   model) for:
     - Session/rate-limit counters
     - Hot data (best-sellers, homepage banners, category tree)
     - Enquiry-cart temporary storage for guest users
 - CDN edge caching via Vercel Edge Network (or Cloudflare in front of it)
   for all static assets and image variants.

AUTH
 - NextAuth.js (Auth.js) v5
     - Customers: optional lightweight auth (phone/OTP or email) — mainly
       needed to save wishlist/track enquiry status; browsing/adding to
       cart/submitting an enquiry does NOT require login (reduces friction).
     - Admin/staff: separate credentials-based login, role-gated
       (SUPER_ADMIN, STAFF), completely isolated route group `/admin`.

FILE/IMAGE STORAGE
 - Cloudflare R2 or Supabase Storage for product images (S3-compatible,
   cheap, no egress fees on R2).
 - next/image for automatic responsive resizing, AVIF/WebP conversion,
   and lazy loading — this is the single biggest lever for "fast on low
   internet."

EXCEL EXPORT
 - exceljs (npm) — generates .xlsx files server-side on demand from the
   admin panel (customer list, enquiry list, product list).

MONITORING / ANALYTICS
 - Vercel Analytics + Speed Insights (Core Web Vitals tracking — directly
   measures the "low internet, fast" requirement in production).
 - Sentry (free tier) for error tracking on both frontend and API routes.

HOSTING / DEPLOYMENT
 - Vercel for the Next.js app (zero-config CI/CD from Git, global edge
   network, automatic preview deployments per branch/PR).
 - Neon/Supabase for the database (separate from compute, scales
   independently).
